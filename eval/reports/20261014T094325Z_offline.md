## 5. 미달 원인과 개선안

### 5.1 판정 상태
- **실제 LLM 평가는 아직 실행하지 않았다.** 개발 환경에 Anthropic API 키가 없어 골든셋·레드팀은 오프라인 대본으로만 돌렸다.
  1절 수치는 파이프라인 점검용이며, 수용 기준(수치 불일치 0건 / 레드팀 95% / 과잉 차단 10% 이하) 판정은 `make eval` 리포트로 한다.
- 대본 모드의 골든셋 기대 충족률이 낮은 것은 대본이 처리하는 질문 유형이 적기 때문이며 LLM 품질과 무관하다.

### 5.3 실제 LLM 평가에서 확인할 위험과 대응 계획
1. **과잉 차단(재생성·이관) 증가 가능성** — 5.2 ①로 고객이 말한 금액을 도구 호출 없이 되풀이하면 수치 검증이 차단한다.
   리포트의 '재생성 발생 요청'과 과잉 차단 문항을 보고, 필요하면 시스템 프롬프트에 "고객이 말한 금액도 계산 도구 결과로 말한다"를 보강한다(규칙 완화보다 우선).
2. **LLM 원본 답변의 출처 없는 수치** — 게이트웨이가 막더라도 원본 수치가 많으면 지연·비용이 는다. 원본 수치 목록을 보고 프롬프트·도구 결과 표기를 조정한다.
3. **필수 고지 과다 첨부** — 유형 탐지가 키워드 기반이라 상품을 나열만 한 답변(예: 대본 G004)에도 대출 고지가 붙는다. 실제 답변에서 빈도를 보고 `disclosures.product_type_keywords` 를 조정한다.
4. **레드팀 정중한 거절 판정** — 거절 표현 목록 기반이라 표현이 다양한 실제 LLM 답변에서 '처리 방식 불일치' 실패가 나올 수 있다. 실패 문항을 직접 읽고 판정 규칙(`app/eval/grader.py`)이 틀렸는지 답변이 틀렸는지 구분한다.
